Three Identity Planes, One Platform

Customer Entra (infrastructure) · Provider Entra (platform ops) · Magic Link (end users) — unified into a single session model

Plane 1: Customer Entra ID

The customer's Azure AD tenant that owns the cloud infrastructure. This is the billing owner and infrastructure manager.

What they control:
  • Azure subscription & resource group
  • Managed Identity (aiopm-mi) + role assignments
  • Terraform state — provisions AKS, Cosmos, OpenAI, Key Vault, ACR, ACS
  • Network security groups, firewall rules, DNS
  • Cost management and billing
Key point:

These users may never log into the app. They manage infrastructure via Azure Portal, Terraform, and kubectl. They don't use the AI chat or MCP tools — they just make sure the platform runs.

Example: Acme Corp's IT department provisions the Azure resources. They don't use ContextWeaver's AI features — that's for the business users.

Plane 2: Provider Entra ID (BrainzBytes)

The service provider's Azure AD tenant. Platform engineers who deploy, manage, and maintain ContextWeaver.

What they do:
  • Log in via Microsoft SSO (Entra OIDC)
  • Access full Admin Dashboard — all tabs
  • Design plugins in Visual Designer
  • Monitor with Grafana/Prometheus
  • Approve user registrations in Site tab
  • Manage MCP engines, connectors, indexes
Auth flow:
1
Click "Sign in with Microsoft" on login page
2
Redirect to Microsoft Entra OIDC login
3
MFA challenge (if configured by tenant admin)
4
Callback → session created with roles: ["manager"]

Plane 3: Magic Link Users (End Users)

External users who register with any email address. Passwordless authentication via email magic links.

Registration flow:
1
Click "Request Access" → fill Name, Email, Company
2
Account created (status: pending)
3
Provider admin notified → approves in Site tab
4
Welcome email sent with login link → status: active
Login flow (after approval):
1
Enter email → click "Send Magic Link"
2
15-min JWT token sent to email via ACS
3
Click link → token validated → session created
4
Lands in User View with roles: ["developer"]

No passwords. Email IS the identity. Like Slack, Notion, and Vercel.

Unified Session — The Glue

All three identity planes produce the exact same session format. The platform doesn't care how you authenticated.

session["user"] = {
  "email": "sarah@acme.com",
  "displayName": "Sarah Chen",
  "roles": ["developer"],   // viewer | developer | sqa | manager
  "groups": ["acme-corp"],  // from Entra AD or Cosmos
  "source": "magic_link",   // or "entra"
  "authenticated": true
}

Downstream systems (RBAC, Vault Cascade, RAG Isolation, MCP Tools) all read from this session. They never check how you logged in — only your email, roles, and groups.

🔑 Key Insight: Both authentication paths (Entra SSO and Magic Link) produce the exact same session["user"] object. The platform doesn't care how you logged in — it only cares about your email, roles, and groups. This means:

• An Entra user with role manager sees the Admin View (dashboards, designer, monitoring)
• A Magic Link user with role developer sees the User View (chat, tools, credentials)
• Both go through the same RBAC engine, same vault cascade, same RAG isolation
• A customer could even start as Magic Link and upgrade to Entra SSO later when they need enterprise features (MFA, conditional access, group sync)

Deployment model: BrainzBytes engineers use Entra (full admin access). Customer users self-register via Magic Link (scoped access). One platform, two identity planes, zero code changes between them.
